Game Table Rendering

The virtual tabletop — rendering, camera, drag-and-drop and selection for live play.

Overview

src/ui/table/ implements the game table itself — the screen a player spends almost all of a session looking at. It is a direct Lua port of the Flutter client's lib/ui/table_screen.dart, split across four files with a clean separation of concerns:

FileLinesResponsibility
table_screen.lua~1870The screen object: state, input handling, drag lifecycle, context menus, dialogs, hotkeys, and the top-level draw/update entry points.
table_view.lua~950Pure layout and drawing: the camera transform, the felt/sidebars/player-row/hand-fan rendering, and recording hit-test "items" and drop zones for table_screen.lua to consume next frame.
card_render.lua~340Drawing a single card (face or back, image or code-drawn fallback) at an arbitrary position/scale/rotation, plus the large hover-preview overlay.
selection.lua~60Pure geometry helpers for box-selection hit-testing and keeping dragged items on the table — deliberately free of any love.* call so it can be unit-tested directly (see Tests & Tools).

The screen is handed a live session and controller pair: session (src/game/session.lua) is the read model — authoritative table state plus a few client-only conveniences like drag previews — and controller (src/game/controller.lua) is how this screen requests changes (move a card, flip it, shuffle a pile, etc.), which get validated against src/core/table_actions.lua before taking effect, then broadcast to every seat. Nothing in this directory mutates game state directly; it only reads session.state and calls controller:* methods.

A single table-screen instance also serves three different contexts with minor behavioral differences, all threaded through its constructor opts: a local offline/practice game, a hosted multiplayer game (src/net/host_server.lua), and a joined server game (src/ui/screens/server/*) — the latter additionally sets deckStore, collectionMode (hides the Pack Generator and Card Library) and spectator (disables all drags, menus and card hotkeys).

table_screen.lua — state & behavior

src/ui/table/table_screen.lua
The game table screen object: owns per-frame derived state, box selection, drag & drop, hotkeys, context menus, dialogs and in-game overlays (game menu, log, library, search, hover preview).

Construction and derived state

T.new(opts) copies every field of opts onto self, then initializes camera state (zoom = 1, camX/camY = 0), animation tables (rotAnim, wiggle), the hit-test item lists (items, prevItems, dropZones), selection state, and loads this game's playmat images (T:loadPlaymats, scanning <gameFolder>/_playmats for png/jpg/jpeg/webp files and shuffling their order — F12 cycles through them in-game, see below).

T:derive() runs once per frame, at the very top of draw, and rebuilds a self.derived table from the live session.state: it buckets every card into hand / zone / table groups, groups table cards into piles via stack_utils.groupByStack, sorts pile roots by top-card z-index, computes which widgets dock into owned zones, and runs seat_utils.computeHandRowLayout to decide which player panels go in the top row vs. bottom row of the screen (this is what makes a 1v1 game show your hand at the bottom and the opponent's at the top, while bigger player counts wrap around). Every other method on T reads from this freshly rebuilt self.derived rather than walking session.state itself.

Selection model

Selection is tracked as two id sets, self.selection.cards and self.selection.tokens (instance ids), but T:refreshSelection() — called every frame right after derive() — is what turns raw card-id membership into the pile-level view the rest of the code actually uses: self.selRoots (pile root id → true) and self.selCount. A pile counts as selected the moment any of its cards is selected, provided its top card still belongs to the acting player (so a pile you no longer own, or that changed hands, silently drops out of the selection on the next frame — there is no explicit "deselect on ownership change" code path; it falls out of recomputing from scratch every frame). Tokens follow the same drop-stale-entries pattern via T:isSelectableToken.

T:toggleSelected(item) implements Ctrl+click: for a token it flips one id in sel.tokens; for a pile it flips every card in that pile's group together, so partial-pile selection is impossible. T:finishBoxSelect(b) implements drag-to-box-select: it converts the dragged world-pixel rectangle to screen space, then tests it against self.prevItems (not the items just drawn this frame — see why below) using selection.boxHits, adding every owned tableCard/pile item's whole pile and every selectable token it touches. T:selectedCards() and T:selectedTokenIds() are the read-side accessors nearly everything else (drag, context menus, hotkeys) builds on.

Hotkeys (keyboard)

T:keypressed(key, _, isrepeat) is the dispatcher. Escape is special-cased first: it clears an active selection/box-select before it's allowed to toggle the game menu, and is swallowed entirely while a menu or the log is open. While the game menu or log has focus, nothing else processes (except L to close the log). A spectator gets only the view-only subset (camera reset, border toggle, color-tint toggle, playmat cycle, log). Everyone else gets the full table of hotkeys documented in CONTROLS.md: Q/E rotate (T:rotateHovered), X discards (T:discardHovered), F flips (T:flipHovered), Z sends to back (T:sendHoveredToBack), digits 1–9 draw that many cards (T:drawNFromHovered, via a DRAW_KEYS lookup covering both the number row and numpad), plus camera/view toggles. Every one of these first checks T:hoveredSelectionRoots() — if the card under the cursor is part of the current multi-selection, the hotkey acts on the whole selection instead of just that one card, exactly as documented in CONTROLS.md ("F, Q / E, X and Z on a selected card act on the whole selection").

Continuous camera panning (W/A/S/D, PAN_SPEED = 600 px/s) and the Tab/Space/Alt modifier flags are polled every frame in T:update(dt) rather than on key events, since they need to behave like "held", not "pressed once".

Drag & drop pipeline

Dragging is a three-stage state machine threaded through T:processInput() (called once per frame from draw, before anything is actually drawn, against last frame's hit-test items):

  1. Press — T:pressSource(src, mx, my) records self.pending = { src, pressX, pressY } without starting a drag yet. src is built by T:sourceFor(item), which knows how to turn each draggable item kind (tableCard, pile, handCard, zone top card, counter, token, packGenerator, deckHeader) into a generic { kind, ..., cx, cy, scale } descriptor. T:applySelectionToPress(item, src) intercepts this for cards/tokens: Ctrl+click swaps in a toggle-selection click handler instead of a drag; pressing an already-multi-selected item upgrades the source to kind = "selection" so the whole selection drags together; pressing an unselected item while something else is selected clears the selection first.
  2. Threshold — while self.pending exists, each frame checks whether the mouse has moved past DRAG_THRESHOLD = 4 px; if so T:startDrag() promotes it to self.drag. If the mouse is released first instead, it's treated as a plain click (src.onClick runs) — this is how clicking a pile draws its top card, and clicking a shuffle button, Save Deck, or a practice-mode avatar all work through the same pressure-sensitive path.
  3. Drag — self.drag.started = true; T:drawDragFeedback() renders the floating card(s)/widget/selection under the pointer every frame (with a card easing its scale toward hand-size over the hand or table-zoom over the table, GHOST_SCALE_RATE), and for single-card/pile drags with a live primaryId, T:sendCardPreview() throttles (PREVIEW_THROTTLE = 0.05s) a controller:previewCardDrag call so every other connected player sees a ghost of the card moving in real time (rendered by table_view.lua's drawRemoteGhosts). Releasing the mouse calls T:endDrag(), which dispatches to one of handleCardDrop, handlePileDrop, handleWidgetDrop, handleTokenDrop, handleLibraryDrop, or handleSelectionDrop based on drag.kind.

Each handle*Drop function encodes exactly the drop rules documented in CONTROLS.md:

  • T:handleCardDrop — Alt+drag on a multi-card pile (T:pickupGroup, see below) moves the whole visual stack together via T:moveItemsBy; dropping on your hand inserts at the index T:handDropIndex computes from the hand's live screen-space card centers; dropping on a docked zone returns it there (Alt = bottom); Alt+drop near another loose card within STACK_HIT_RADIUS stacks onto it only if session:canStackOnto allows it (piles never mix owners); anything else moves it to that table point, clamped fully onto the table by selection.clampWorldCenter.
  • T:handleSelectionDrop — the same rules generalized to the whole selection: dropping on the hand deals every selected card in, in order; Alt+drop onto a stack target requires every selected card to pass canStackOnto or nothing moves (no partial stacking); otherwise the whole group translates together by the same world-pixel delta, using T:selectionAnchorWorld to compute the offset from whichever item was actually grabbed.
  • T:handleTokenDrop — Ctrl while dropping duplicates the token (controller:duplicateWidget) instead of moving the original; dropping within range of a card attaches it (controller:attachWidgetToCard); otherwise it's just moved.

T:pickupGroup(dragged) computes "every card visually stacked on top of the dragged one" by a breadth-first flood fill over cards that overlap in world space and have a higher z-index — this is what makes Alt+dragging a card also carry along anything resting on it (including attached widgets, handled separately in drawDragFeedback and the drop handlers via groupIds).

Context menus

Right-click is handled as its own press/release pair (self.rightPressItem) so a menu only opens if both the press and release land on the same item. T:openItemMenu(item, mx, my) is the dispatcher: it special-cases a right-click on a card or pile that's part of a 2+ item selection to show T:selectionMenuItems instead of the single-item menu. T:cardMenuItems(card, onSearch) builds the standard per-card menu — "Send to..." submenu (Hand, Discard, and every other card zone, each itself expanding to Top/Shuffle Into/Bottom via the shared placementMenu helper), Flip, a Rotate submenu (T:rotateMenu), and — only for table cards not inside a pile — "Give to <player>" per connected opponent and "Remove Ownership", both routed through T:confirmGive which asks before anything leaves your ownership. Right-clicking empty table opens T:openBoardMenu (Widgets submenu: Simple Counter, Token, and — unless collectionMode — Pack Generator and, only if the game defines deck-building zones, Deck Widget; plus Card Library, also hidden in collection mode).

Dialogs and overlays

Several prompts are built with overlays.dialog (see the UI toolkit): T:promptSetValue/promptSetColors for counters, T:promptSetTokenColor, and T:promptLoadDeck (delegates to deck_library_dialog.lua, documented on Screens). T:saveDeckWidget(w) reconstructs a DeckConfig/SubDeck (see core/models.lua) by tallying the cards currently sitting in each of the deck widget's synthetic sub-zones (deck_widget_zones.lua), then hands it to the same save-deck dialog used elsewhere. T:saveLog() writes the session's action log to the game's folder via save_files.lua.

Full-screen overlay panels share a common chrome drawn by the local panel(id, w, h, title, onClose, trailing) helper (scrim that closes on an outside click, dark rounded panel, title row with a close button) and are layered in a fixed order at the bottom of T:draw: search results (T:drawSearch, for "Search..." on a pile/zone), the Card Library (T:drawLibrary, its own instance of the shared card_filter_bar, temporarily swapping in the dark theme), the Space hover-preview (T:drawPreview, always on top of those but under the menu/log), the Game Log (T:drawLog, virtualized — it only text-shapes and draws rows currently in the visible scroll range despite measuring every entry's height up front since "logs are small"), the Game Menu (T:drawGameMenu — Leave/Save/Settings/Controls plus, for a hosting player, a kick list), and finally whatever is being dragged, so it always renders on top of every dialog.

table_view.lua — camera, layout & drawing

src/ui/table/table_view.lua
Everything about where things are drawn: the pan/zoom camera transform, the felt/sidebar/player-panel layout, hand fanning, and recording this frame's hit-test items and drop zones onto the screen object (T) passed in.
This file has uncommitted local edits in the working tree at the time this documentation was written (git status shows M src/ui/table/table_view.lua). The description below reflects the content currently on disk.

The world/canonical/screen coordinate pipeline

Table positions exist in three coordinate spaces, and table_view.lua is where all the conversions live:

  • Canonical — the coordinates actually stored in game state (card.x, card.y), seat-relative and mirrored so that rules logic never needs to know which physical seat is "yours". Converted via src/core/geometry.lua's canonicalToLocalPixel/localPixelToCanonical, wrapped here as V.canonicalToWorld/V.worldToCanonical (and the T.isMirrored flag — set per seat — is what actually flips the board for the far player in a 2-player game).
  • World — a fixed WW x WH pixel rectangle (geometry.worldWidth/worldHeight) representing the whole table surface, independent of window size or zoom.
  • Screen — actual pixels on screen, after the camera (T.camX, T.camY, T.zoom) and the table viewport rect (T.tableRect, computed by V.layout) are applied: V.worldToScreen / V.screenToWorld.

V.clampedCamera(T) keeps the pan within V.maxPan(T), which allows panning out to geometry.tablePanMarginFraction (M) beyond the table edge in each direction — this is the margin selection.clampWorldCenter also respects when pulling a dropped card back onto the table, so "off the table" and "off the pannable area" agree. V.toScreen and V.screenToCanonical(Clamped) are the composed convenience functions nearly every drag/drop calculation in table_screen.lua actually calls.

Hit-test items and the one-frame lag

V.addItem(T, item) appends to T.items as things are drawn, automatically tagging the item with T.drawMirror if it's currently being drawn inside a rotated region (see withRotated below) so V.hitTest can transform mouse coordinates back into the item's own frame. Critically, input processing reads T.prevItems — last frame's list — not the one being built this frame (table_screen.lua swaps prevItems = items at the end of every draw). This one-frame lag is what lets hit-testing happen before drawing each frame without the two ever racing each other, at the cost of hit-test geometry always being exactly one frame stale — invisible at 60fps but worth knowing when reasoning about edge cases.

V.hitTest(item, mx, my) supports three hit shapes: an axis-aligned box (default), a rotated box (when item.angle and half-extents item.hw/item.hh are set — used for table cards, which must be hit-tested in their own rotated frame), and a circle (item.circle — used for tokens and the shuffle button). withRotated(T, rotate, x, y, w, h, fn) is the mechanism behind drawing an opponent's panel upside-down in a >2-player game: it pushes a 180° graphics rotation around the panel's center and sets T.drawMirror for the duration of fn, so every item registered inside automatically gets a mirrored hit test later.

Drawing the table surface

V.drawTable(T) clips to T.tableRect and draws, in order: the center playmat marker (drawCenterMarker — a rounded rectangle outline with the current playmat image cover-fit and stencil-clipped inside it), table piles (drawTablePiles), board widgets (drawTableWidgets), arrows (drawArrows), other players' in-flight drag ghosts (drawRemoteGhosts), the discard-flight animation (drawFlight), and the active box-selection rectangle (drawSelectionBox).

drawTablePiles is the richest of these: for each pile root it draws either a single card (1 card) or a pile box with a count badge and, for the local player's own non-opponent piles, a shuffle button (drawPileBox, also reused for zones and deck-widget sub-zones — it's the shared "a stack of cards with a count badge" renderer). Rotation (V.cardTurns) folds together seat-mirroring, the card's defined orientation (portrait/left/right), and any manual quarter-turns from Q/E, and V.animatedTurns eases between rotation states over ROT_DURATION = 0.15s using a cubic ease-out. V.ghostAlpha(T, id) dims a card to 30% opacity while it's being dragged locally or previewed as being dragged by someone else.

Widgets each have a dedicated face-drawing function reused both for their resting position and for drag feedback: counterFace (rounded square, auto-shrinking number text), packFace (shows the game's configured pack-generator art, or a text fallback), tokenFace (a plain colored circle), and deckWidgetFace (the most complex: a header with a drag handle and owner label, one sub-zone pile box per deck-building zone defined by the game, and — for the owner only — a "Save Deck" button strip at the bottom).

Player panels and the hand fan

drawPlayerRow lays out one row (top or bottom) of player panels side by side, each composed of a hand band, that player's owned zone slots, and an avatar corner — and the order these three are drawn in flips (reverse) depending on seat position so panels visually mirror correctly across the table. drawHandBand draws one player's hand: for the local player it's the actual playable fan (T.derived.localHand); for anyone else it's just a count of face-down card backs.

The fan shape itself — fanLayout(P, count, innerW) — places cards along a circular arc: it picks an angle step up to the user's configured tilt-per-card, capped so the total spread never exceeds maxSpread, then derives the arc radius from the configured horizontal step and shrinks it further if needed so the fan's outer corners (accounting for tilt and the hover-lift) still fit within the available width. All of these shape parameters — card scale, spacing, tilt, max spread, raise, reveal — come from hand_settings.lua (**Settings > Hand**, per CONTROLS.md), read fresh each frame via V.handParams(). A hovered card eases upward (FAN_LIFT_RATE, exponential easing toward P.lift) so it can be read without fully leaving the fan, and the hit box (kind = "handCard") is grown vertically to cover both its resting and lifted position so the hover doesn't flicker at the boundary.

V.layout(T, x, y, w, h) runs once per frame before any drawing to compute T.layoutRects (left/right shared-zone sidebars, top/bottom player rows) and T.tableRect (whatever space is left in the middle) — shared zones with side == "left" or "right" (per the game definition) reserve a fixed-width sidebar column drawn by drawSidebar.

card_render.lua — drawing a single card

src/ui/table/card_render.lua
Draws one card (face or back) at a base size under a transform, so every caller positions by center with an independent scale and rotation. Also the standalone "big preview" renderer used by the Space-hold feature and the card pool/shop/collection screens.

Every card is drawn at a fixed base size, R.cardWidth = 70 × R.cardHeight = 100 (R.radius = 3.5 corner radius), under a love.graphics.push/translate/rotate/scale/pop transform — so the same drawing code works identically whether it's rendering a 70×100 table card at T.zoom, a larger hand card, a 4/3-scaled pool tile in the Deck Editor or Collection screen, or a huge hover-preview copy.

R.draw(opts)

The single entry point everything else in the app uses to draw a card. opts: def (a CardDefinition or nil for an unknown/opponent card), faceUp, cx/cy (screen center), scale, angle (radians), border/tint/alpha (color overlays — border draws the owner-colored outline, tint is the translucent selection-color overlay), cardBacks (the game's card-back definitions, needed to resolve what a face-down card should actually look like), and forceFaceUp (used by previews that must show the face regardless of the card's real state).

Face/back drawing falls through three tiers, handled by imageFace: (1) if the definition's image is already decoded in the image cache, draw it cover-fit into the card rect with rounded corners via a small custom shader (roundedShader — discards pixels outside a rounded rect computed in the destination's own coordinate space, with a graceful pcall fallback if shader compilation ever fails); (2) if it's still decoding, draw a plain gray placeholder; (3) otherwise fall back to a code-drawn face (codeDrawnFace) — a colored rectangle using the card's colorHex, with the title and a suit glyph (♥♦♣♠, from SUIT_GLYPHS) printed in opposite corners, mirroring the classic playing-card layout. Card backs without a defined image get an analogous code-drawn pattern (codeDrawnBack — a blue card with a crosshatch and diamond motif) or, if the game specifically has configured card backs but none resolves for this card, a red "missing" warning card (missingBack).

R.shownOrientation(def, showingBack, cardBacks) and R.orientationTurns(o) translate a card's declared orientation (portrait/left/right) into a quarter-turn fraction, used throughout table_view.lua wherever a card's drawn angle is computed. Text drawn inside the transformed card (scaledPrint) quantizes its own font size to quarter-scale steps so LÖVE reuses font objects instead of rasterizing a new one on every tiny zoom change, while undoing that quantization in the print call so text still renders crisply at the exact requested scale.

R.drawPreview(faces, cardBacks, sw, sh, mx)

The large hover-preview renderer used by the Space hotkey everywhere in the app (table, deck editor, shop, collection, trade). faces is a small list of { def, faceUp, orientation } — usually one, or two when R.definitionFaces(def, cardBacks) is used to show both a card's front and its distinct back. It stacks the faces vertically, sized so a single face fills up to 70% of the screen height (90% for a stack) while staying under 42% of the screen width, and centers the stack in whichever half of the screen (left or right of mx, the cursor x) is farther from the mouse, so the preview never covers the thing being previewed.

Small helpers also live here because they're purely about drawing a card-adjacent decoration: R.drawEmptySlot (dashed-looking rounded outline for an empty zone), R.drawCountBadge (the black circular "×N" pile-count badge), and R.drawSearchBadge (the eye icon shown on a pile/zone currently being searched).

selection.lua — box-select geometry

src/ui/table/selection.lua
Pure geometric helpers for table box-selection hit-testing and keeping moved items fully on the table. No love.* calls, so these are unit-tested directly (see tests/table_actions_test.lua and tests/selection_test.lua in Tests & Tools).
S.rectFromPoints(x1, y1, x2, y2)

Normalizes two arbitrary corner points (the box-select drag can go in any direction) into a {x, y, w, h} rect with non-negative width/height.

S.boxHits(rect, item)

Does a box-select rectangle touch a given hit-test item? Three cases, mirroring table_view.lua's V.hitTest shapes: a circular item (tokens) tests distance from the circle's center to the nearest point on the rect; a rotated item (angled table cards) first computes the rotated shape's axis-aligned bounding box (via |cos|/|sin| projections of its half-extents) and then does a plain box overlap against that — a conservative approximation (a rotated card's corner can be "selected" slightly before the box visually touches its edge) that keeps the hit test cheap; anything else is a plain axis-aligned rectangle overlap.

S.halfExtents(w, h, turns)

Returns the half-width/half-height of a w x h box after being rotated by a number of full turns, swapping width and height whenever the nearest quarter-turn is odd (90°/270°) — used wherever code needs "how much space does this card actually occupy on screen right now," e.g. when clamping a drop position.

S.clampWorldCenter(wx, wy, halfW, halfH)

The function behind CONTROLS.md's "Anything that would end up partly off the table is pulled back fully onto it." Given an item's half-extents, it clamps its center so the item's full extent stays within the table plus the pan margin (geometry.tablePanMarginFraction) in from S.EDGE_MARGIN = 10 world pixels — the same margin the camera itself is allowed to pan into (see V.maxPan), so a card can be dropped anywhere the camera could currently see. If an item is simply too large to fit within the margins on an axis (shouldn't normally happen for cards), it falls back to centering on that axis.
