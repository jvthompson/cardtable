Running the test suite

CardTable has no external test framework — it ships a ~130-line hand-rolled runner and runs entirely inside the LÖVE executable, launched in a special mode rather than as a separate script. From the project root: 

lovec . --test
lovec . --test selection      -- only tests whose full name contains "selection" (case-insensitive)

main.lua checks for the --test flag before anything else loads. If present, it sets the global TEST_MODE = true (read in conf.lua, see architecture.html), and love.load takes a completely different path than the real app: instead of calling src.app.load, it calls the local runTests(args) function:

  1. It scans the optional second CLI token: if the token right after --test doesn't itself start with --, it's taken as a name filter and threaded through to the runner.
  2. It lists every file in the tests/ folder via love.filesystem.getDirectoryItems, keeping only names matching _test%.lua$, and sorts them alphabetically so runs are deterministic.
  3. It calls require("tests.runner").run(files, filterArg) (documented below).
  4. It quits the process with love.event.quit(ok and 0 or 1) — a real, scriptable exit code, so the suite is CI-friendly even though it's "just" a LÖVE game binary.
Isolated save identity. conf.lua's love.conf branches on the same TEST_MODE flag: it sets t.identity = "cardtable_tests" (LÖVE's save-directory identity, normally "cardtable") and disables the window, audio, sound and joystick modules. This means test runs read and write an entirely separate save folder from a real play session — tests that create settings, save files, scratch directories, avatars, etc. (see data_test.lua below) can never clobber the user's actual profile, decks or saved games, and can run headless.

tests/runner.lua — the harness

tests/runner.lua
Minimal BDD-style test harness: registration (describe/it), assertions, and a text report.

The module builds a table T that every *_test.lua file receives as its single argument. There is no global test registry or auto-discovery magic beyond the filename scan in main.lua — each test file is a Lua chunk that returns a single function(t) ... end, and the runner loads, calls, and aggregates results from each in turn.

Grouping and naming

T.describe(name, fn)

Pushes name onto a prefixStack, calls fn immediately (synchronously — there is no deferred scheduling), then pops. Nesting describe blocks nests the prefix.

T.it(name, fn)

Builds the test's full dotted name as "file_test > describe... > name" via fullName (joined with " > "). If a filterArg was supplied, the test is skipped unless the lower-cased full name contains the lower-cased filter as a substring — this is how --test selection narrows to one file's tests without needing exact matches. Otherwise it runs fn under xpcall; a thrown assertion failure (a table with testFailure = true) or any other Lua error is caught, given a traceback via debug.traceback, and recorded into results.failures. Passes increment results.passed.

Assertions

FunctionChecks
t.eq(actual, expected, msg?)Deep structural equality (deepEqual, below) — the workhorse assertion used almost everywhere in this suite, since most production functions return whole Lua tables (card instances, table states, deck configs, …).
t.ok(v, msg?)Truthy.
t.notOk(v, msg?)Falsy.
t.isNil(v, msg?)v == nil exactly.
t.near(actual, expected, eps?, msg?)Numeric tolerance compare (default eps = 1e-9) — used for floating-point geometry and offset math.
t.errors(fn, msg?)Passes only if calling fn() raises (via pcall).
t.ids(list, key?)Not an assertion — a helper that maps a list of model instances to just one field (default "instanceId"), so assertions can compare short id lists instead of whole objects.

deepEqual(a, b) recursively compares tables key-by-key in both directions (so extra keys on either side fail the comparison) and falls back to == for non-tables — it is exposed as T.deepEqual and underlies t.eq. serialize(v, depth) renders a Lua value as a compact literal ({a=1, b="x"} style, numeric array part first, keys sorted, depth-capped at 3) purely to build readable failure messages — it is not used for anything functional.

Running a batch and reporting

T.run(files, filterArg) → allPassed:boolean

For each file path, loads it with love.filesystem.load, calls the returned chunk to get the file's function(t), sets prefixStack to that file's base name (stripped of the _test.lua suffix) as the outermost name segment, then pcalls the registration function with T itself. A failure to even load/register a file (e.g. a syntax error) is recorded as its own failure entry named "<file> (load)". After every file has registered and run its t.it blocks, it prints FAIL: <name> plus the indented error/traceback for every failure, then a one-line "N passed, M failed" summary, and returns whether the failure count was zero (this becomes the process's exit code via main.lua).

tests/helpers.lua — shared fixtures

tests/helpers.lua
Terse constructors for the core model types, used by nearly every other test file to avoid repeating full field lists.

Builds on src/core/models.lua's model constructors (CardInstance.new, BoardWidgetInstance.new, PlayerInfo.new, TableState.new, CardDefinition.new) by filling in sane defaults for every field a test doesn't care about:

HelperPurpose
H.card(f)A CardInstance defaulting to zone="table", face-down, z-index 0; accepts either f.instanceId or the shorter f.id.
H.widget(f)A BoardWidgetInstance defaulting kind="token"; copies every field from f first, so it also accepts kind-specific fields (value, attachedCardId, etc).
H.player(id, name?, role?, color?)A PlayerInfo, defaulting the role to "client" and the name to the id.
H.state(f)A TableState with empty players/cards/revision 0/widgets/searches/log unless overridden — the standard starting point for exercising table_actions.lua.
H.find(list, id, key?)Linear search by id (default key instanceId) — the main way tests pull a single card/widget back out of a mutated state to assert on it.
H.cardDef(id, types?, extra?)A minimal CardDefinition (title defaults to the id) with an optional types list and a free-form extra field overlay.

models_test.lua

Cross-links: core.html — models.lua, color.lua, and the shared lib/json.lua encoder (also documented on core.html).

What would silently break without it: any drift between how a model is read from JSON and how it's written back — the single most load-bearing property this file protects is round-trip fidelity (decode → model → encode reproduces the original bytes, field order included), because save games, decks and game definitions are the actual user-facing file formats on disk, shared with the original Flutter app.

  • json round-trip quirks — large integers stay integral (no 4283782756.0), doubles print shortest-round-trip, key order is preserved on encode (object fields aren't re-sorted), Dart-style pretty-printing matches exactly, unicode/surrogate-pair escapes decode correctly, and malformed JSON (tryDecode) fails softly instead of throwing.
  • color hex conversions (color.hexFromColor/colorFromHex) round-trip and fall back to a caller-supplied default on bad input.
  • CardDefinition, CardInstance, BoardWidgetInstance, ZoneDefinition — every field round-trips, and encoding omits fields still at their default value (so a freshly-created record serializes to a minimal JSON object, matching what the original Flutter client would write) while still writing an explicitly-false boolean like faceUp when it differs from a type's implied default. util.copyWith(..., { field = util.NIL }) (see util.lua) is exercised as the way to explicitly null out a field.
  • GameDefinition — cards nested inside sets get stamped with their set's id on load and are written back without a redundant setId (since nesting already implies it); legacy flat cardBackImagePath migrates into the newer cardBacks list; deckTypes/needsDeckBuilding derive correctly from zones that dealsBuiltDeck. A full round-trip of the bundled assets/games/standard_52/standard_52.json asset is checked byte-for-byte at a fixed point (decode→encode→decode→encode == itself) — this is the test most likely to catch a breaking change to the on-disk game-definition schema.
  • DeckConfig — the old flat entries format throws a structured { legacyDeckFormat = true } error rather than silently misparsing; isStarter is optional, case-insensitive on read (IsStarter), and only written when true; DeckConfig.full(game) builds a one-of-everything deck.
  • TableState / SavedGame / LogEntry / ActiveSearch / PlayerInfo round-trip together as a whole saved-game graph; formatElapsedTime and buildStandardDeckCards (the built-in 52-card deck used when a game asks for a "standard deck" zone, see core.html) are spot-checked.

utils_test.lua

Despite the filename, this is the broadest single test file in the suite — a condensed port of seven separate Dart test files. It exercises most of core.html's pure logic modules directly against hand-built states from helpers.lua, with no I/O.

  • seat_utils.computeHandRowLayout (seat_utils.lua) — for 2, 3 and 4-player tables, verifies which seats land in the viewer's own "bottom row" vs. the opposing "top row", and that far-side viewers see a mirrored/rotated arrangement rather than the same absolute seating — this is what lets every player's screen show "me at the bottom" regardless of turn order.
  • geometry.lua (geometry.lua) — table-centering offsets, vertical clamp of a card's center against table bounds including a pan margin, and the canonical-(0..1)-to-pixel conversion (and its inverse) used for every card and widget position on the table.
  • deck_widget_zones.lua (deck_widget_zones.lua) — the synthetic zone-id scheme (deckWidget:<widgetId>:<realZoneId>) used so a player-placed Deck Widget can have its own private main/side/discard zones; checks the id round-trips even when the real zone id itself contains colons, and that malformed strings parse to nil rather than a partial/garbage table.
  • state_filter.filterForRecipient (state_filter.lua) — the server-authoritative "fog of war" function: opponents' hand cards and the contents of private (non-shared, non-visible) zones are replaced with a generic hidden-card placeholder (models.hiddenDefinitionId) for a given recipient, while a player's own hand, shared zones, and the open table stay untouched. This is the single function standing between "secret information" and a cheating client, so its test coverage (own hand vs. others', private vs. shared vs. explicitly-visible zones, deck-widget synthetic zones) is a correctness-critical boundary.
  • pack_generator.selectPackCards (pack_generator.lua) — the Pack Generator widget's and the server's collection-mode pack algorithm: with no tag settings picks N distinct cards; with tag settings (e.g. "2 Rare") it fills each tag quota without double-counting a card that matches two tags; it degrades gracefully (shortfall) when the pool doesn't have enough matching cards rather than erroring; and with a seeded RNG (util.seededRng) it is fully deterministic — which both tests and the real server (for provably-fair pack opening) rely on.
  • card_filters.lua (card_filters.lua) — sort orders (name/set/race-tag-group) and the combined filter predicate (cardMatchesFilters: tag selection, tag exclusion, set exclusion, free-text search) used by the Card Library, Deck Editor and gamedef editor's card browsers.
  • save_remap.lua (save_remap.lua) — re-loading a saved game with a different set of connected players: matchPlayersByName maps saved player ids to current ones by display name (and correctly refuses to guess when names are ambiguous/duplicated), and buildLoadedTableState rewrites every card/widget owner id through that map, drops cards whose definition no longer exists in the game, clears dangling stackParentId references into cards that got dropped, and preserves revision/log/searches structure. This is what makes "load a save with a different group of friends" not corrupt state.
  • ui.clampLines (src/ui/kit/ui.lua) — word-wrap-aware text truncation with a trailing ellipsis, tested against a fake monospace font stand-in so it runs headless without a real font.

table_actions_test.lua

Cross-link: core.html — table_actions.lua, the pure state-transition functions that are the actual rules engine (every card/widget move, flip, draw, shuffle, stack and deck-widget operation on the table).

What would silently break without it: this is the largest and most important test file in the client, because table_actions.lua is the authoritative game logic shared verbatim between the LÖVE client's local/practice mode and the Go server's embedded engine (see server.html) — a regression here is a regression in actual gameplay rules, not just test coverage.

  • moveCard / moveStack / moveGroup — repositioning detaches a card from any pile/zone, always produces a new immutable state object (never mutates the input — every test checks s.revision == 0, "original state untouched"), bumps z-index to bring the moved thing to front, drags along attached widgets (tokens stick to the card they're on), and a multi-select group move translates every passenger by the primary's delta while still re-ordering z front-to-back.
  • Ownership on move — cards flagged unownable (set by a game's rules, e.g. community cards) lose their owner the instant they're set loose on the table; normal owned cards keep theirs.
  • rotateStack / flipCard / giveCard / sendToBack — rotation only applies to table cards (not hand cards), accumulates across repeated calls, flipping toggles faceUp and still bumps z, and giveCard changes/clears ownerId.
  • stackCard — the pile-forming operation: snaps onto the target's position, links stackParentId, clears any zone membership and (for unownable cards) ownership; is a safe no-op stacking onto itself or a missing target.
  • moveToHand / reorderHand — picking a card up always makes it face-up, strips zone/stack links and resets rotation; reordering within a hand is index-based and clamps out-of-range indices to the end, leaving other players' hands untouched.
  • drawCard / drawFromZone — drawing from a pile always takes the physically topmost card first and only reaches the pile's root/anchor card last; a count-based draw happens as a single state revision (not N separate revisions) and clamps the count to what's actually available; drawing from a zone correctly enforces/ignores ownership depending on whether the zone is private or shared.
  • returnToZone — returning a card to a zone snaps it to the zone anchor's position, can go to the top (default) or bottom (toBottom) of the pile, picks up ownership from the zone's owner (or stays unowned for a shared zone), and respects an explicit face-up/face-down flag; a card already in that zone is a no-op.
  • shuffleZone / shufflePile — shuffling always flips every card face-down and reassigns a contiguous new z-order (checked by sorting the resulting z-indices), and is a no-op for a single-card zone/pile.
  • Searches (startSearch/stopSearch) — starting a second search for the same player replaces (doesn't duplicate) their entry; stopping a search that doesn't exist is a true no-op (same table reference returned, not just equal).
  • Widgets — creation, arrows, free movement (which detaches any card attachment and zeroes the stored offset), re-attaching to a card (which recomputes a relative offset), value/color setting (setWidgetValue clamps into [0, 99999]), and duplication (copies kind/value/colors, not position). deleteWidget on a Deck Builder widget specifically "spills" every card that was living in that widget's private synthetic zones back onto the open table (restoring ordinary ownership rules) rather than deleting the cards — this is the one case in the file with genuinely non-obvious, must-get-right behavior.
  • dealNewCards — appended cards always get freshly-assigned ascending z-indices regardless of whatever z-index they arrived with (so a client can't desync the stacking order by sending arbitrary z values).

selection_test.lua

Cross-links: ui-table.html — src/ui/table/selection.lua, core.html — geometry.lua (world size constants).

What would silently break without it: box-selection hit testing and the "keep everything on the table" clamp used after every drag — both involve rotated-rectangle and circle geometry that's easy to get subtly wrong at the edges.

  • rectFromPoints normalizes a drag in any of the four directions into a positive-width/height rect.
  • boxHits — axis-aligned rect-vs-rect overlap for ordinary items; for a rotated card it uses the card's actual rotated bounding box (a card rotated 90° has a wider effective hit box than its unrotated footprint, and the test specifically catches the case where the naive unrotated box would miss a selection the rotated one should catch); for widgets with a circular hit area it tests distance-to-closest-point-on-the-box against the radius, including the tricky corner case.
  • halfExtents swaps width/height for any odd quarter-turn (90°/270°, in either rotation direction, including angles greater than one full turn) and keeps them for even turns.
  • clampWorldCenter — leaves fully-on-table items alone, and otherwise pulls an item's center back so it stays within the table's pan margin from any of the four edges, using the item's rotated half-extents so a turned card isn't allowed to poke further off-table than an unrotated one would be.

session_test.lua

Cross-link: game.html — src/game/session.lua and src/game/controller.lua.

What would silently break without it: the orchestration layer above table_actions.lua — dealing decks into zones at game start, the human-readable game log line generated for each action, host-side ownership enforcement, and the client-side network request serialization. A regression here either corrupts a new game's starting layout or produces wrong/missing log entries and network payloads, which is much harder to notice in manual testing than a broken card move.

  • Session.dealFromZones — the single function that sets up a fresh table: deals each player's configured deck into zones marked dealsBuiltDeck (falling back to one copy of every card in the game if no deck config was supplied for a player), respects optional vs. required sub-decks (a missing optional subdeck just deals nothing instead of erroring), deals static zone entries and honors a zone's faceUp flag, creates one widget per kind = "widget" zone (e.g. a shared life-counter) seeded with its configured starting value/color, deals shared zones (pool/discard/standard-52/named-deck-by-zone-id) with correct emptiness and unownable-card handling, and — when a zone is marked autoShuffle — shuffles while preserving the exact multiset of cards and assigning a clean sequential z-order.
  • Practice seats — in local practice mode a single human can act as any seat (setActiveSeat) and actingPlayerId() follows that; the same call is a no-op for a real (non-practice) hosted session, since who you're "acting as" there is fixed to your network identity.
  • Action log generation — this is the largest block of the file: every mutating call on Session (moveCard, flipCard, drawCard, drawFromZone, shufflePile/shuffleZone, returnToZone, giveCard, rotateStack, moveToHand, widget value/attach changes, searches, pack generation, card-library creation, deck loading) appends a specific, exactly-worded log line, and the test pins the exact English wording (e.g. 'Alice played "Ace" to the table from hand.' vs. the generic "Alice played a card to the table from the Draw Deck." when the card came from a zone other players can't see into). It also confirms non-shuffleable zones silently decline to shuffle (no log line, no revision bump), that connect/disconnect events log only on change and never for the host, and that deck-widget synthetic zone ids resolve back to a real, nameable zone in log text without leaking which synthetic sub-zone was used.
  • Stacking rules (ownership-aware, routed through Session rather than called directly on table_actions) — a card only stacks onto a pile with the same effective owner (unowned/unownable cards treated as a third "owner"); stacking that would mix owners is silently refused (no error, no state change) rather than allowed or logged; giving away a card that's part of a pile never changes its owner (only the detached top of a stack is up for grabs).
  • Arrow widgets expire — a drawn arrow (Tab+drag on the table, per CONTROLS.md) is removed by Session:update() once 5 simulated seconds have passed, using an injectable now() clock so the test doesn't need a real wall-clock sleep.
  • Controllers (game.html — controller.lua) — controller.Host is the authority wrapper: it enforces that a client can't move another player's card and resolves ambiguous "my shared-zone draw" vs. "another player's private zone of the same id" semantics using the active seat. controller.Client is the non-host, network-facing half: every action method serializes to a specific message type/payload shape (requestMove, requestGiveCard, requestMoveGroup, requestReturnToZone, requestStopSearch) and the test pins the exact JSON emitted, because this wire format must stay compatible with the original Flutter client/server (see net.html and server.html).

data_test.lua

Cross-link: data.html — this single file (the longest test file by line count) covers the majority of src/data/*, plus one UI module and one platform module it happens to share fixture needs with.

What would silently break without it: file-format compatibility with the original Flutter app's on-disk layout, and correctness of path/image/profile handling across Windows' quirks (case-insensitive extensions, non-ASCII paths, landscape-vs-portrait card art).

  • Game loader (game_loader.lua) — the bundled standard-52 definition loads all 52 cards; gamedef.json is found case-insensitively while ignoring unrelated files in a game folder; image paths on cards/sets/backs resolve relative to the right subfolder; a malformed file is reported as a load error (not a crash) and a missing folder yields an empty list rather than erroring; a game library scan appends the built-in standard-52 "game" automatically and expands any zone that requests a standardDeck.
  • Image resolver (image_resolver.lua) — bare-path resolution with an optional subfolder; mergeLocalImagePaths (used when joining a multiplayer game hosted by someone else: the host's card data arrives over the network, but image paths must point at the local copy of that game's folder, dropping any image the local copy doesn't have); the full default/alternate/unique/missing card-back resolution chain, including the special __unique__ back that looks for a sibling <cardfile>_BACK.ext file; pack-generator and game-logo image discovery.
  • Gamedef ops (gamedef_ops.lua) — name/path helpers (case-insensitive extension checks, path-equality across slash styles, unique-id generation like a → a_001 → a_002); copying picked images into a game folder, including a feature where landscape-oriented PNGs get auto-rotated to portrait when building card art from a folder of images (verified pixel-exact via a marker pixel) but only when explicitly requested; building a full set of CardDefinitions directly from a folder of image files (auto-detecting which files are "back" art by a _BACK suffix match against a supplied name list); writing a pretty-printed gamedef.json with bare (non-absolute) image paths; game-id validation (rejects empty/"..", otherwise permissive); scanning a whole game library sorted by display name; detecting duplicate card ids and duplicate card images across a game (and a "merge duplicate image cards" operation that unions their type tags); finding cards that don't belong to any defined set (which a save/export step would otherwise silently drop); extracting "rarity" tags from a game's tag groups; and a from/to directory migration helper used when the user moves their games library location.
  • Deck library (deck_library.lua) — scanning a game's user-saved decks together with any built-in decks shipped inside the game folder, flagging old-format deck files as "legacy" rather than erroring, filtering strictly to the right game id, and deck-name validation.
  • Save files (save_files.lua) — write → list → read round-trips a full SavedGame; listing is newest-first and silently skips a corrupt save file rather than failing the whole listing; log export formats elapsed-time-prefixed lines and writes them next to other log files without disturbing unrelated ones; save/log filenames follow a fixed, parseable naming scheme.
  • WebP decoding (image_utils.lua, image_worker.lua) — this test is conditionally skipped when no libwebp*.dll is sitting next to the executable (WebP support is optional/best-effort on Windows); when present, it round-trips a lossless-encoded image both through the main-thread decode path and through a real love.thread worker thread (the same code path used for actual card-art decoding off the main thread), confirming both agree on dimensions and pixel content.
  • Avatar handling (profile.lua) — saving a profile avatar resizes anything wider than 256px down to a 256-max bounding box (preserving aspect ratio) while leaving smaller images alone, and replaces any previously-saved avatar file even if it had a different extension (so a user switching from a .jpg to a .png avatar doesn't end up with two stale files).
  • Hand settings / table settings (hand_settings.lua, table_settings.lua) — numeric settings clamp into valid ranges, only get persisted to the underlying key-value settings.lua store when they differ from the default (so a never-touched install has an empty settings file), and a "transient" set variant can skip persistence entirely; reset() removes the stored override rather than writing back the default value.
  • Recent servers (profile.lua) — the "Join Game" recent-server list caps at 5 entries, de-duplicates by host:port by moving the existing entry to the front instead of adding a second one, and supports removing a single entry.
  • Controls dialog markdown parser (src/ui/screens/controls_dialog.lua) — controls.parse turns CONTROLS.md's actual Markdown (headings, pipe tables, bold lines, bullet lists, paragraphs) into a block list the in-game Controls dialog renders with the custom UI toolkit (ui-framework.html) rather than a browser — since CONTROLS.md is read directly from the packaged game at runtime, this test both checks the tiny parser's block-kind detection and inline bold/code handling, and incidentally guarantees the file is present and parseable in the build.

net_test.lua

Cross-links: net.html — src/net/upnp.lua, platform.html — src/platform/discord.lua.

What would silently break without it: the string/XML parsing inside UPnP port-mapping (the actual network call to a router can't be exercised in CI, so this is the only safety net for that logic) and Discord Rich Presence join-secret parsing.

  • UPnP — case-insensitive LOCATION header extraction from an SSDP discovery response; resolving a device's relative controlURL against its description-document URL (absolute, root-relative, and already-absolute-URL cases) plus a base-URL splitter; scanning a device's XML service list to find specifically the WAN IP connection service (not the sibling WAN common-interface or PPP services that can appear in the same list) and extracting its control URL, including tolerating stray whitespace inside the XML tag; and building the exact SOAP XML envelope body for an AddPortMapping call.
  • Discord — parseJoinSecret extracts host/port from a secret shaped "host:port" and rejects malformed ones; before discord.init() has ever been called, every Discord API surface (setIdle, update, fetchInvitableFriends, ensureAuthorizedAndConnected) must behave as a safe no-op/failure rather than erroring — this matters because the app runs fine with --no-discord or when the Discord SDK simply isn't available.

server_client_test.lua

Cross-link: net.html — src/net/server_client.lua and src/net/protocol.lua.

What would silently break without it: the lobby/room client's request-response correlation and event routing — the layer that turns raw protocol messages from the Go server into the callbacks and typed events the UI screens consume.

Uses a hand-written fake connection object (records every send, replays a queued inbox on poll) rather than a real socket, so these tests are pure logic tests with no actual networking:

  • Password hashing — pins the exact algorithm (sha256("cardflux:" .. email .. ":" .. password)) the client must use so it matches the Go server's own hash, and confirms the email is case/whitespace-normalized first (so "Alice@Example.COM " and "alice@example.com" hash identically).
  • Request/response correlation — outgoing requests get sequential rids, and responses are matched back to their original callback by rid even when they arrive out of order; if the connection drops while requests are still pending, every pending callback fires with a synthetic {error = "disconnected"} rather than hanging forever.
  • Message routing — lobby-level messages (lobbyState, tokens) update the client's own cached state directly, while in-game messages (gameData, fullState) are forwarded to a separate "game channel" object rather than handled inline — this is the seam between the lobby UI and the actual game table. Closing the current room clears roomId and fires a roomClosed event with the reason.
  • Scheduled shutdown — a serverShutdown push both fires an event with the countdown and pops a warning dialog through the shared overlay system (ui-framework.html) directly from the networking layer.
  • Trading — a tradeInvite push fires its event; a trade push seeds the running trade state and its chat log only on the *first* push for a given trade id, and a repeat push for the same trade does not duplicate the already-seeded chat; a plain chat message tagged with a tradeId is appended to the separate tradeChat list, never to lobby/room chat; closing a trade clears the cached trade object and reports why.

platform_test.lua

Cross-link: platform.html — src/platform/updater.lua, winproc.lua, winhttp.lua.

What would silently break without it: the self-update mechanism's release-selection and shell-quoting logic — bugs here either fail to detect a real update or, worse, generate a broken/dangerous PowerShell helper script.

  • buildFromTag extracts the numeric build suffix from a GitHub tag like v0.1.0+49 (and returns nil for tags without one, or a nil input) — this is how the updater compares "newer" independent of the name version string (see src/version.lua's comment on why the LÖVE port numbers builds separately from the Flutter app).
  • pickRelease only returns a release when its build number is strictly greater than the current one and it actually carries an asset with the expected exact filename — a release missing the asset, or GitHub's "Not Found" error body, both yield nil rather than crashing the update check.
  • pathsInside filters a list of folder paths down to just the ones nested under the install directory — specifically so the updater's directory sync can exclude a user's game_library/deck_library folders from being overwritten, while not accidentally matching a similarly-named sibling install folder.
  • helperScript — the generated PowerShell script text that performs the actual file swap (robocopy ... /MIR plus an exclude list) after the app exits; the test pins exact single-quote escaping of paths containing an apostrophe (C:\It's Here → C:\It''s Here), which is exactly the kind of bug that would otherwise only surface on a specific user's machine.
  • winproc.quoteArg — Windows command-line argument quoting (backslash-before-quote escaping rules), tested against the classic edge cases (trailing backslash before a closing quote, embedded quotes).
  • winhttp.parseUrl — accepts only https:// URLs (the updater never downloads over plain HTTP), splitting host/port/path and defaulting the port to 443.

asset_worker_test.lua

Cross-link: net.html — src/net/asset_worker.lua.

What would silently break without it: the client's game-asset cache reuse logic — getting this wrong means either re-downloading images the player already has (wasting their bandwidth and the server's) or, worse, silently keeping a stale/corrupted file that doesn't match what the server actually has.

Runs the real worker as a genuine love.thread (not a mock), talking to it over love.thread.newChannel() exactly as production code does, but pointed at 127.0.0.1:1 (a port nothing listens on) so any attempt to actually download fails loudly — meaning a passing test proves the file was served from a local source, not silently fetched over the network:

  • A file already sitting in the destination cache folder — even if LÖVE never "knew" about it — is matched by SHA-256 and reused with zero network activity.
  • A file can be found and copied from a local game-library folder carrying the same game id, without needing to be in the asset cache at all.
  • A file can be found and copied from another previously-connected server's own asset cache under the same game id (so switching between two servers hosting the same game doesn't force a re-download).
  • If a locally-available file has the right size but different content (hash mismatch), it is correctly treated as not matching — the job reports an error (since nothing else to fetch it from is configured in the test) rather than silently accepting the wrong bytes, and the mismatched local file is left untouched rather than overwritten.

deck_editor_test.lua

Cross-link: ui-screens.html — src/ui/screens/deck_editor.lua.

What would silently break without it: deck-building slot grouping and, in collection-mode, the enforcement that a player can't put more copies of a card into a deck than they actually own — a client-side mirror of a rule the server also enforces (see server.html), but one that must still be right locally so the editor's own UI (copy counts, what's shown in the pool) doesn't lie to the player.

  • Slot building (DE.buildSlots) — a game with no deck-building zones gets a single implicit main_deck slot labeled "Deck"; otherwise zones are grouped by their deckType into one slot per type, labeled after the first zone of that type, and a slot is "required" if any zone of that type is non-optional (so one optional and one required zone sharing a type still makes the combined slot required).
  • Editing (DE.Editor) — adding/removing copies preserves insertion order in the resulting deck config; separate deck-type slots (e.g. main vs. side) are tracked independently via activeDeckType; loading an existing DeckConfig populates the editor and silently drops any card id the current game doesn't define (protecting against decks exported from a different/older version of a game).
  • Collection-mode ownership limits — copies of a normal card are capped at the player's owned quantity across every slot combined (so you can't put the same owned copy into both a main deck and a side deck); cards marked unownable or isFreeCard are always available in unlimited quantity and are treated as implicitly owned by the card pool filter; loading a deck that calls for more copies than are owned trims it down to what's actually owned, with later slots losing out first when there's a shortfall; the pool view (visibleCards) only shows cards the player owns at least one copy of, plus unownable/free cards.

tools/compat_check — library compatibility tool

tools/compat_check/main.lua
tools/compat_check/conf.lua
A separate, standalone LÖVE program (its own conf.lua, its own entry point) — not part of the test suite and not run by --test.

It is invoked directly as its own LÖVE project, pointed at a real, user-owned CardTable game/deck library (typically the original Flutter app's data folder) rather than at fixtures: 

lovec tools/compat_check <libraryRoot> [--all-images]

where <libraryRoot> must contain a game_library/ and a deck_library/ subfolder.

Why this exists as a separate tool, not a test

The unit test suite only ever exercises small, hand-built or synthetic fixtures — it never has access to (and should never depend on) a real user's actual game collection, which can contain arbitrarily large sets of custom games, decks and save files that vary machine to machine and were authored by the other, Flutter-based CardTable client. compat_check exists specifically to answer "does this Lua port read everything a real Flutter-authored library already has on disk, and does re-saving it stay faithful to the original bytes/schema?" — a question that is about compatibility with external, pre-existing data rather than about the port's own internal correctness, and that can't be captured as a small deterministic fixture. It is meant to be run by hand against a developer's or tester's real library, not in CI.

What it checks

It walks every game in game_library/ via game_loader.lua, and for each one:

  • Round-trips the raw gamedef.json bytes through decode→model→encode and classifies the result as identical, identical except Dart's 1.0-vs-1 number formatting, a known/expected migration (legacy cardBackImagePath → cardBacks, which the original Flutter app itself performs on save), merely reordered (same data, different key order — harmless), or a genuine DATA DIFFERS problem, in which case it prints a structural JSON diff (path-by-path, capped at 8 differences) of exactly what changed.
  • Verifies every card's image file actually exists on disk, and — either for one sample file per extension (default) or for every single image when run with --all-images — that it actually decodes via image_utils.decodeFile.
  • Checks that every card using the special __unique__ card back actually has a matching <name>_BACK.<ext> file (noting, rather than failing, that the Flutter client shows an error placeholder for the same case rather than crashing).
  • Confirms the game's logo and pack-generator images (if any) resolve.
  • Round-trips every built-in deck and every save file found inside the game's own folder the same way as the game definition, and separately flags any save that references a card id no longer defined in the game.
  • Then walks deck_library/ similarly: for every deck file under a per-game subfolder, it flags a folder name that doesn't match any loaded game, classifies old-format deck files as expected rejections ("old format (Flutter also rejects it)") rather than errors, round-trips readable decks, and flags decks referencing unknown card ids or declaring a gameId that doesn't match the folder they're filed under.

All output is both printed to the console and written to compat_report.txt in the tool's own save directory, and the process exits non-zero if any problem was found — so it can still be wired into a manual release checklist even though it isn't part of automated CI.
