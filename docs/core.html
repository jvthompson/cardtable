Why this folder is special: one ruleset, two runtimes

Every file documented on this page — plus lib/json.lua and src/game/session.lua / src/game/host_engine.lua (documented on Game Session & Controller) — has no dependency on LÖVE or any UI code. They only use the Lua standard library (plus, for uuid.lua, an optional love.math RNG with a plain math.random fallback). That isolation is deliberate: this exact set of files is copied verbatim into the companion Go server at server/engine/lib/json.lua, server/engine/src/core/*.lua and server/engine/src/game/{session,host_engine}.lua, and executed there inside the Go server process by gopher-lua, a pure-Go Lua VM — see server.html for how that embedding works. A PowerShell script, server/tools/sync-engine.ps1, copies the client's copies over the server's copies; the server/README.md's development section is explicit that after changing any of these files in the client, you must re-run that script and rebuild the server or the two sides of a networked game will silently disagree about the rules.

The upshot: the client (running LuaJIT inside LÖVE) and the dedicated lobby server (running gopher-lua inside a Go binary) enforce exactly the same Lua source code for what a move is legal and what a table looks like after it. The server doesn't reimplement card-game logic in Go — it runs the client's own logic. This is the single most load-bearing architectural fact in the whole codebase.

Conceptually the files split into three layers: models (models.lua defines every on-disk/over-the-wire shape), pure state transitions (table_actions.lua, the only place a TableState is actually mutated — copy-on-write, never in place), and small focused helpers (geometry, color, seats, stacks, filters, pack-opening, save-remapping) that the models and transitions layer, and the UI layer documented elsewhere, build on.

lib/json.lua — JSON codec

lib/json.lua
Minimal JSON encoder/decoder tuned for exact compatibility with the original Flutter app's JSON files (saved games, decks, gamedefs, settings) and reused as the wire format for the network protocol.

Three properties make this more than a toy codec, called out in its own header comment:

  • Decoded arrays/objects carry a metatable that marks their JSON type (__jsontype), so an empty [] round-trips as an array and an empty {} round-trips as an object even though both decode to an empty Lua table.
  • Objects built with json.object() (or any table whose metatable carries an __order list) keep key insertion order when re-encoded; anything else gets alphabetically sorted keys, for deterministic output.
  • Integral numbers are written without a fraction or exponent — important because ARGB color ints (0xFFRRGGBB) can exceed 231 and must stay exact integers, not switch to scientific notation.
json.null
A sentinel table (not Lua nil) representing JSON null, since a Lua table can't store a real nil value under a key.
json.object(pairsList) -> table
Builds an ordered object from a flat list of alternating keys/values (e.g. json.object({"id", 1, "name", "x"})); a value of nil is skipped. Every model's toJson in models.lua goes through this (via a local obj(...) wrapper).
json.array(t) -> table
Tags a plain Lua list table as a JSON array (forces [] encoding even if empty).
json.isArray(t) -> boolean
True if t carries the array metatable, or — for a plain table with no metatable — if its keys are exactly the contiguous integers 1..#t.
json.encode(v, opts) -> string
opts.indent (e.g. " ") pretty-prints to match Dart's JsonEncoder.withIndent(' ') byte-for-byte, which matters because save files and gamedefs were originally written by the Flutter predecessor app and need to stay diffable/compatible.
json.decode(str) -> value
Strips a UTF-8 BOM if present, then parses. Throws a Lua error with a line/column-annotated message (decodeError) on malformed input. Inside an object, a JSON null value is dropped (the key is simply absent) rather than stored — only a top-level or array-element null decodes to the json.null sentinel.
json.tryDecode(str) -> value|nil, err
Protected wrapper around decode using pcall; returns nil, errorMessage instead of throwing.

models.lua — the data model

src/core/models.lua
The single source of truth for every shape that gets saved to disk, sent over the network, or edited by the Game Definition Editor. Header comment calls it a "port of lib/models/*.dart" — the original Flutter app's model classes, reimplemented as plain Lua tables.

Every model follows the same three-function pattern: Kind.new(fields) (fills in defaults for missing fields), Kind.fromJson(t) (validates required fields via a local requireField and decodes), and Kind.toJson(obj) (re-encodes, omitting any field that equals its own default via unlessDefault — this reproduces the original Dart app's sparse JSON output exactly, field order included). To update an existing model instance immutably, callers use util.copyWith(obj, {...}) from util.lua; passing util.NIL as a change value explicitly clears that field (Lua can't store a literal nil inside a changes table the way Dart can pass an explicit null).

CardBackDefinition

Fields: id, name (required), imagePath, orientation (default "portrait"). GameDefinition.fromJson migrates a legacy single cardBackImagePath field into a one-element cardBacks list with id "default", so older gamedef files keep loading.

PackSetting / GameSet / TagGroup

  • PackSetting: {tag, count} — pack generation for a tag (consumed by pack_generator.lua). count's integer part is a guaranteed number of cards of that tag; its fractional part is the chance of one additional card of that tag on top of the rest of the pack.
  • GameSet: {id, name, packSettings} — a named set/expansion whose cards live under it in the gamedef's sets array.
  • TagGroup: {id, name, tags} — a named group of tags (e.g. a "Rarity" group with tags Common/Rare/Mythic), used for filtering and sort order in card_filters.lua and the gamedef editor.

DeckEntry / SubDeck / DeckConfig

DeckEntry is just {definitionId, quantity}. A SubDeck is {name, entries} — one named pile of entries (a game can define multiple deck-building zones with different deckTypes, e.g. "main_deck" and "side_deck", each becoming its own subdeck). A DeckConfig is {gameId, subdecks, isStarter} — a whole built deck for one game.

DeckConfig.subdeck(d, name) / entriesFor(d, name) / cardCountFor(d, name) / totalCardCount(d)
Lookup/aggregation helpers.
DeckConfig.full(game) -> DeckConfig
Builds the "one copy of every card" deck used for practice games with no explicit deck chosen — one subdeck per GameDefinition.deckTypes(game), or a single "main_deck" subdeck if the game defines no deck-building zones at all.
DeckConfig.fromJson(t)
Throws the special error table M.LegacyDeckFormatError ({legacyDeckFormat = true, message = "..."}) if t.subdecks is absent — i.e. a deck file saved before the subdeck format existed. StandardDeck

M.buildStandardDeckCards() -> list of CardDefinition
Synthesizes a full 52-card deck (4 suits × 13 ranks A,2–10,J,Q,K) with ids like __standard52_hearts_A, red/black colorHex by suit, and unownable = true. Used when a ZoneDefinition.standardDeck flag is set, so a game can offer "a normal deck of playing cards" without the game author having to define 52 cards by hand.

TableState

The entire authoritative state of a running game: {gameId, players, cards, revision, widgets, searches, log}. revision is a monotonically increasing integer bumped by every mutating table_actions call — it's both the "has anything changed" signal for Session listeners and the version number the host broadcasts so clients know whether an incoming state is newer than what they have (Session:applyRemoteState ignores anything with revision <= current).

Small, dependency-free helpers ("no love.* dependencies" per its own header) used throughout the whole core/game layer: list operations, a copy-on-write helper, a seeded RNG, and string trimming.

seat_utils.lua — hand layout / mirroring

src/core/seat_utils.lua
Port of lib/game/seat_utils.dart. Decides, for a given viewer, which seats render as "near" (bottom row, their own hand) vs. "far" (top row, opponents) and whether the shared table itself should be mirrored for them.

Seat indices are 0-based, matching the original Dart. The core judgment call:

S.isFarMirrorSeat(seatIndex, playerCount) -> boolean
2 players: seat 1 is far. 3 players: seats 1+ are far. 4 players: seats 2+ are far. 5+: the ceiling of half the seats are far. This is what makes a 1v1 game put your opponent squarely across the table while a 4-player game splits two-and-two.
S.computeHandRowLayout(players, localPlayerId) -> {bottomRow, topRow}
Splits players into near/far lists via the function above; if the viewer themself is a "far" seat, both lists are reversed before being returned as bottomRow/topRow, so the layout always reads correctly from the viewer's own point of view — this is consumed by the hand-rendering code in ui-table.html.
S.isViewerMirrored(players, localPlayerId) -> boolean
Whether the viewer is sitting in a "far" seat and therefore needs the whole shared table mirrored on both axes — feeds directly into geometry.canonicalToLocalPixel's isMirrored parameter.

stack_utils.lua — pile math

src/core/stack_utils.lua
Port of lib/game/stack_utils.dart. A "stack" (pile) on the table is a chain of cards linked through stackParentId, rooted at the bottom card (the one whose stackParentId is nil).
S.rootIdOf(cards, card) -> instanceId
Walks stackParentId links up to the root, guarding against a cycle via a visited set (defensive — a well-formed stack never cycles, but corrupt/replayed state shouldn't infinite-loop).
S.stackOf(cards, rootInstanceId) -> list
Every card in cards whose root resolves to rootInstanceId (including the root itself).
S.groupByStack(cards) -> groups, order
Buckets every card by its stack root in one pass; order is the first-seen order of root ids (mirroring Dart's insertion-ordered LinkedHashMap) so rendering order stays stable.
S.topOf(stack) -> card
The highest-zIndex card in the list; ties favor the earlier card in the list (replicates Dart's reduce with a >= comparison exactly, which matters for deterministic draw order from a pile with duplicate z-indices).

state_filter.lua — hiding private info

src/core/state_filter.lua
Port of lib/networking/state_filter.dart`. Produces a per-recipient view of a TableState before it's sent to a client — the server-authoritative half of "opponents' cards, piles and zones are read-only" (CONTROLS.md) is enforced by never even telling a client what a hidden card is.
F.filterForRecipient(trueState, recipientId, visibleZoneIds) -> TableState
visibleZoneIds is a set {zoneId -> true} of zones whose ZoneDefinition.visibleToAll flag is set. For every card: it's hidden from recipientId if it has an owner that isn't the recipient and either it's in someone's hand, or it's in a private (non-visible-to-all) zone. A hidden card is swapped via util.copyWith to {faceUp = false, definitionId = models.hiddenDefinitionId} — the recipient still sees that a card exists (its position, owner, zIndex) but not what it is.

This is called from host_engine.lua's broadcast() once per player per revision before sending fullState, both when the host is the LÖVE client itself (direct host/join, net.html) and — because this file is one of the ones mirrored into server/engine/ — when the host role is played by the dedicated Go server (server.html).

card_filters.lua — sorting & filtering

src/core/card_filters.lua
Port of the filter/sort logic in lib/ui/widgets/card_sort_menu.dart, shared by the Deck Editor, the Card View tab of the gamedef editor, and the in-game Card Library (right-click menu on empty table). The actual filter-bar widgets live in src/ui/kit/card_filter_bar.lua and filter_menu.lua — this file is the pure logic they call.
F.sortBySet / F.sortByName
String constants for the two built-in sort keys; any other sort key is treated as a TagGroup id.
F.sortCardDefinitions(cards, sortKey, sets, tagGroups) -> list
Returns cards unchanged if sortKey == nil. For sortBySet, ranks by the card's set's position in sets (cards with no set sort last). For sortByName, rank is constant (falls through to the title-based secondary sort). For a tag-group key, ranks each card by the earliest matching tag's position within that group's own tag order (cards matching no tag in the group sort last). All three fall back to case-insensitive title, then original index, for a fully stable sort.
F.cardMatchesFilters(card, tagGroups, selectedTagsByGroup, excludedTagsByGroup, selectedSetIds, searchQuery) -> boolean
Evaluated per-card by the filter bar. Order of checks: (1) if any of the card's tags appears in any group's exclusion set, reject outright; (2) for every tag group with a non-empty selection, the card must match at least one selected tag in that group (groups with nothing selected impose no constraint — this is an AND-across-groups, OR-within-group filter); (3) if any set is selected and the card belongs to a (different) set, reject; (4) finally, a trimmed, case-folded searchQuery must appear (via util.containsText, a literal substring match) in either the card's title or its id.

table_actions.lua — the state-transition engine

src/core/table_actions.lua
Port of lib/game/table_actions.dart. This is where every rule described in CONTROLS.md's "Game table" section — dragging, stacking, flipping, rotating, dealing, drawing, shuffling, searching, and every board-widget operation — actually lives. Every function is a pure function: (TableState, ...) -> TableState. Nothing is ever mutated in place; untouched cards/widgets are shared by reference with the old state (so a caller can cheaply diff old vs. new for logging), changed ones are fresh copy-on-write tables via util.copyWith.
Revision discipline: every op that actually changes something calls the local bumped(state, changes) helper, which sets changes.revision = state.revision + 1. The header comment is explicit that this happens exactly where the original Dart version bumps it — including some ops that bump the revision even when the target id isn't found, because the Dart original didn't guard those cases either. Getting this byte-for-byte identical matters because the server runs this exact file too: any divergence would desync revision numbers between a LuaJIT client and the gopher-lua server.

This file is called almost exclusively from session.lua (never directly by UI code), which wraps each call with permission checks, game-log entries and listener notification — see that page for the full call chain from a mouse drag to a persisted state change.

Internal helpers

nextZIndex(state) -> integer
Exported as A.nextZIndex; one past the current max card zIndex (0 if there are no cards). A parallel private nextWidgetZIndex does the same for widgets, kept as a separate counter space.

Called after any op that moves cards; re-pins every widget with a non-nil attachedCardId to card.x + attachOffsetX, card.y + attachOffsetY, returning the original state unchanged (no new allocation) if nothing actually needed to move.

A.moveCard(state, instanceId, x, y)Moves a single card to the table at (x,y), clearing stackParentId/zoneId (detaches from any pile/zone) and clearing ownership if the card is unownable. Bumps z to front and re-syncs attached widgets.
A.moveStack(state, rootInstanceId, x, y)Moves an entire pile together; only the top card of the pile gets a new (frontmost) zIndex, the rest keep their relative order.
A.rotateStack(state, rootInstanceId, clockwise)Adds ±1 to rotationTurns on every card in the pile that's currently on the table (not in a zone/hand); only the top card's zIndex is bumped.
A.sendToBack(state, rootInstanceId)Re-zIndexes just the pile's top card to the new backmost value.
A.moveToHand(state, instanceId, ownerId)Sends a card into ownerId's hand face-up, clearing pile/zone attachment and rotation.
A.reorderHand(state, instanceId, ownerId, targetIndex)Reorders one owner's hand (A.handCards, stable-sorted by zIndex) by removing the card and re-inserting at the clamped 0-based targetIndex, then re-issuing contiguous zIndexes to the whole hand.
A.flipCard(state, instanceId)Toggles faceUp and brings the card to front.
A.giveCard(state, instanceId, newOwnerId)Reassigns ownership (forced to unowned if the card is unownable or newOwnerId is nil) and brings it to front.
A.stackCard(state, instanceId, ontoInstanceId)Stacks one card onto another: adopts the target's position/zone and sets stackParentId = ontoInstanceId. No-op if the two ids are equal or the target isn't found. (Ownership-compatibility — "piles never mix owners" — is enforced one layer up, in Session:canStackOnto, not here.)
A.moveGroup(state, primaryInstanceId, passengerRootInstanceIds, x, y)Moves a multi-select: the primary card goes exactly to (x,y) (clearing pile/zone like moveCard); every passenger pile is translated by the same delta the primary moved, keeping the whole selection's relative layout — this backs "Drag a selected item" from CONTROLS.md.

No-op below 2 cards.

deck_widget_zones.lua — synthetic zone ids

src/core/deck_widget_zones.lua
Port of lib/game/deck_widget_zones.dart. A board-placed Deck Widget (see right-click > Widgets > Deck Widget, only offered when a game defines deck-building zones) needs its own private zone namespace, separate from the game's fixed ZoneDefinitions — this file mints and parses those ids.
D.build(widgetInstanceId, realZoneId) -> string
Returns "deckWidget:<widgetInstanceId>:<realZoneId>".
D.isDeckWidgetZoneId(zoneId) -> boolean
Simple prefix check.
D.parse(zoneId) -> {widgetInstanceId, realZoneId}|nil
Splits the synthetic id back apart; returns nil on anything malformed (missing separator, empty real zone id). Used throughout session.lua and host_engine.lua wherever a zone-owning widget needs to be resolved (e.g. Session:zoneDefinition unwraps the synthetic id to find the underlying ZoneDefinition, and host_engine:zoneOwnerId resolves a deck-widget zone's effective owner to whoever owns the widget itself).

pack_generator.lua — pack-opening algorithm

src/core/pack_generator.lua
Port of lib/game/pack_generator.dart. The single algorithm behind both the table's Pack Generator board widget (free play) and the dedicated server's collection-mode card shop — server/README.md states the shop uses "the same algorithm as the Pack Generator widget, using each set's pack settings." See shop.lua and server.html for the two call sites.
P.defaultPackCardCount
10 — how many cards a pack contains when none of the set's PackSettings guarantees at least one card (its count floors to 0 or there are no settings at all).
P.selectPackCards(setCards, packSettings, rng) -> list of CardDefinition
Each setting's count can be fractional and is read in two parts. Phase 1 (the normal pack): math.floor(count) is a guaranteed number of cards of that tag — the pool of not-yet-picked cards in the set carrying that tag is shuffled and up to that many are taken. If every setting floors to 0 (including when there are no settings at all), this phase instead shuffles the whole set and takes the first defaultPackCardCount cards, ignoring tags entirely. Phase 2 (the bonus chance): each setting's fractional remainder (count - floor(count)) is the probability of one additional card of that tag on top of whatever phase 1 produced — e.g. count = 1.5 means a guaranteed 1 plus a 50% chance of a 2nd; count = 0.5 alone means a 50% chance of 1 bonus card on top of the default fill. A card is never picked twice (tracked via a pickedIds set) and a pool smaller than what it's asked for is never padded — a pack can legitimately come back short. rng is an optional seeded generator (see util.seededRng) used both for shuffling and for each bonus-chance roll; it defaults to math.random.

save_remap.lua — reloading saved games

src/core/save_remap.lua
Port of lib/game/save_game_remap.dart. When a saved game is reloaded, the people sitting down to play it now are almost never the exact same PlayerInfo objects (new ids each session) — this file reconciles old player identities with new ones, by name, and rebuilds a playable TableState around the match.
R.matchPlayersByName(savedPlayers, currentPlayers) -> {matched, unmatchedSaved, unmatchedCurrent}
Matches a saved player to a current player only when the name is unique on both sides (if two saved players shared a name, or two current players do, neither is auto-matched — ambiguous cases are left for the caller, presumably the load-saved-game UI, to resolve manually). matched maps saved-id → current-id; the two unmatched lists are the leftovers on each side.
R.buildLoadedTableState(saved, currentPlayers, savedIdToCurrentId, validDefinitionIds) -> TableState, droppedCardCount
Rebuilds the saved state for today's players: players list is re-filtered/re-mapped to only the current players that matched; every card whose definitionId isn't in validDefinitionIds (the game's definitions may have changed since the save was made) is dropped entirely, and the drop count is returned so the UI can warn the user; every surviving card's ownerId is remapped through savedIdToCurrentId (or cleared to unowned if its old owner has no match); any card whose stack parent got dropped has its stackParentId cleared rather than pointing at a card that no longer exists; widgets are remapped the same way for ownerId/creatorId/attachedCardId. Unlike the original Flutter app, the game log is preserved as-is on reload — its entries name players the way they were at save time, which the header comment calls out as a deliberate difference.
